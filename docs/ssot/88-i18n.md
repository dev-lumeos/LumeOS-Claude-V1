## Sprachpräfix in der Adresse — ja oder nein

**Nein.** Die Sprache kommt aus einem Cookie, die Adresse bleibt
`/v2/nutrition` — kein `/de/`, kein `/en/`.

`[read]` **Das ist keine Umgehung, sondern ein vorgesehener Betriebsmodus
von next-intl.** Die Bibliothek führt dafür eine eigene Beispielanwendung
(„App Router without i18n routing") und eine Einstellung
`localePrefix: 'never'`. Der Weg ist dokumentiert: `getRequestConfig`
liest das Cookie, `NextIntlClientProvider` im Wurzel-Layout reicht die
Texte weiter. Genau so gebaut.

**Warum nicht mit Präfix — drei Gründe, der Reihe nach:**

1. **Kollision mit der Parallelstruktur.** `[cmd]` Die neue Oberfläche
   liegt unter `/v2`, die alte unter `/nutrition`. Mit Präfix entstünde
   `/de/v2/nutrition` — ein Pfad mit zwei Bedeutungsebenen, von denen
   eine (`/v2`) ausdrücklich vorübergehend ist.

2. **Doppelter Umbau bei G-07.** `[read]` Dort wird `/v2` hochgezogen.
   Ohne Präfix ist das ein Umbau. Mit Präfix wären es zwei: erst
   `/de/v2/nutrition` → `/de/nutrition`, dann die Frage, was mit den
   Bestandslinks passiert.

3. **Die Sprache gehört zur Person, nicht zur Seite.** `[read]` Tom
   will sie im Profil — „damit sie über Geräte hinweg gilt". Eine
   Einstellung, die an der Person hängt, in die Adresse zu schreiben,
   erzeugt zwei Wahrheiten: die im Pfad und die im Profil.

**Was es kostet** — ehrlich benannt:

| | |
|---|---|
| Kein Deep-Link je Sprache | `/v2/nutrition` sieht für alle gleich aus. Wer einen englischen Stand teilen will, kann das nicht über die Adresse. |
| Suchmaschinen | Ohne eigene Adresse je Sprache gibt es nichts zu indizieren. `[annahme]` Für eine angemeldete Anwendung ohne öffentliche Seiten ist das folgenlos — sollte später eine öffentliche Landeseite dazukommen, ist das neu zu entscheiden. |
| Statisches Ausliefern | Seiten, die die Sprache brauchen, müssen je Anfrage gerendert werden. `[cmd]` Beide umgestellten Seiten sind ohnehin `force-dynamic` — sie lesen Sitzungsdaten. |

Der Cookie heisst `lumeos-sprache` und läuft ein Jahr. **Dieselbe
Mechanik wie Theme und Modus** — der Server kennt den Wert beim ersten
Rendern und schreibt `lang` direkt ins HTML, es blitzt keine falsche
Sprache auf.

## Die Prüfung (A-15)

`tools/i18n-pruefen.mjs`, in `pnpm gate` **vor** Turbo — `[cmd]` die
Zahl der Tasks bleibt bei **8**.

`[read]` **Der Anlass:** next-intl erkennt fehlende Schlüssel in
Zweitsprachen nicht zur Übersetzungszeit. Sie fallen erst zur Laufzeit
auf, und dort wird stillschweigend zurückgefallen — ein Schlüssel, den
nur `de` kennt, sieht in `en` aus wie eine Übersetzung und ist keine.

**Was die Prüfung tut:**

| | |
|---|---|
| `de` ohne Entsprechung in `en` | **rot** |
| `en` ohne Entsprechung in `de` | **rot** — beide Richtungen |
| Leere Zeichenkette | **rot**, zählt als fehlend: ein Schlüssel mit `''` ist eine Lücke mit Deckmantel |
| Thai | **gezählt, nicht erzwungen** — die Zahl steht in der Ausgabe |
| Datei fehlt oder ist kaputtes JSON | **rot** |

**Grün sieht so aus:**

```
[i18n] 95 Schluessel je Pflichtsprache (de, en), vollstaendig.
[i18n] th: 0 von 95 belegt — 95 offen (vorgesehen, nicht erzwungen).
```

Die zweite Zeile ist der Umfang eines Übersetzungsauftrags — genau
dafür steht sie da.

### Zum Fehlschlagen gebracht — dreimal

## Was fehlt, damit die Sprache über Geräte hinweg gilt

`[cmd]` Heute hängt die Wahl am Cookie — sie gilt je Browser, nicht je
Person. Für Toms zweite Anforderung („und im Profil") braucht
`public.profiles` eine **`locale`-Spalte**. Das ist Schemaarbeit und
gehört Codex.

**Was gebraucht wird, konkret:**

| | |
|---|---|
| Spalte | `locale text` in `public.profiles`, erlaubt: `de`, `en`, `th`; `NULL` heisst „keine Wahl getroffen" |
| Vorgabe | `NULL`, **nicht** `'de'` — sonst ist nicht unterscheidbar, ob jemand Deutsch gewählt hat oder nie gefragt wurde |
| Prüfung | `CHECK (locale IS NULL OR locale IN ('de','en','th'))` |

**Angeschlossen wird es so:** `request.ts` liest zuerst das Profil, dann
das Cookie, dann die Vorgabe. Die Sprachwahl schreibt beides. `[annahme]`
Der Umbau ist klein — eine Abfrage in `getRequestConfig` und ein
`PUT` in der Auswahl; die Oberfläche selbst ändert sich nicht.
